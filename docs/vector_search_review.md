# 벡터 검색 검토 (2026-11-19) — 검토만, 구현 없음

범위: 지금 키워드 검색(`tutor/search.py`: 낱말 추출 + 동의어 확장 + 질문 문장 가중)이 놓치는 유형을 평가셋 밖 질문 10개로 확인하고, 로컬 임베딩·SQLite 저장·혼합 방식을 비교한다. **코드·검색 설정·동의어는 건드리지 않았고, 패키지도 설치하지 않았다.** 검색 평가 결과를 보고 검색 코드를 고치지도 않았다.

### 놓치는 유형 4가지
1. **일상어 → 시험 용어의 간극**(#2 #3 #4 #10): 사용자는 외상값·장사 접을 때·월세·월급에서 떼는 세금이라고 묻는데 시험 용어는 대손·폐업(잔존재화)·주택임대소득·원천징수다. 지금은 용어 사전(117개)에 있는 일상어만 넓힌다. 이 유형이 4/10으로 가장 많다. **벡터 검색이 가장 도움 될 가능성이 있는 유형**이다.
2. **약어·외래어**(#5 VAT): 사전에 없으면 무매칭. 벡터보다 사전 추가가 값싸다.
3. **흔한 낱말이 점수를 지배**(#2 '처리', #4 '남은', #5 '신고·해야', #10 '받는·세금'): 질문의 핵심이 아닌 낱말이 문항에 걸려 엉뚱한 문항이 상위권에 오른다. 벡터가 아니라 낱말 가중(핵심어 우선) 문제다.
4. **형태 처리 부작용**(#8 `표준원`): 어미 떼기가 명사 끝 글자를 잘라 낸다. 부분 문자열로는 맞아서 결과엔 영향이 작지만, 요약 카드의 '핵심어 세기'에는 영향이 갈 수 있다.

벡터 검색으로 풀리지 않는 것: #9처럼 DB에 그 내용을 다룬 문항 자체가 없을 수 있는 경우, 그리고 유형 3·4.

Hugging Face API 로 라이선스·크기를 확인했다(`license` 태그, 파일 크기). 속도는 **측정하지 않았다**(설치 금지).

## 3. SQLite 에 벡터 저장하는 방법

| 방법 | 장점 | 단점 | 이 프로젝트 적합도 |
|---|---|---|---|
| **A. 일반 테이블 BLOB(float32) + numpy 완전탐색** | 추가 의존성 없음(numpy 이미 있음), 540문항×384차원 ≈ 0.8MB, 코사인 검색이 밀리초, 적재 스크립트(`load_db.py`)에 한 단계 추가 | 문항이 수만 개로 늘면 느려짐(해당 없음) | **최적** |
| B. `sqlite-vec` 확장(0.1.9, MIT/Apache) | SQL 로 근접 이웃 질의 | 이 환경의 Python 3.14 `sqlite3` 에 `enable_load_extension` 이 **없어서**(직접 확인) 확장을 못 불러옴. 다른 Python 빌드가 필요 | 부적합 |
| C. Chroma·FAISS 등 별도 벡터 DB | 기능 많음 | 의존성·저장소 추가, 540문항에는 과함 | 부적합 |

벡터는 문제은행처럼 `data/tutor.db` 의 새 테이블(예: `question_vectors(question_id, model, dim, vec BLOB)`)에 두고, 문제은행 재적재 때 같이 다시 만들면 된다. 풀이 기록(`records`)처럼 사용자 데이터가 아니라 **파생 데이터**라서 재생성 가능해야 한다. 모델 이름·차원을 같이 저장해 모델이 바뀌면 자동으로 다시 만들게 한다.

## 4. 키워드 + 벡터 섞는 방법

| 방법 | 설명 | 장단점 |
|---|---|---|
| **RRF(순위 합치기)** | 키워드 순위와 벡터 순위를 `1/(60+순위)` 로 더해 재정렬 | 점수 단위를 맞출 필요 없고 조정값이 거의 없음. **추천** |
| 후보 재정렬 | 키워드 후보 상위 50개를 벡터 유사도로 재정렬 | 키워드가 아예 못 찾는 경우(#10)엔 후보에 없어 소용없음 |
| 약할 때만 보조 | 키워드 상위 3개의 '맞은 낱말'이 모두 흔한 낱말이거나 결과가 없을 때만 벡터 결과를 덧붙임 | 기존 결과·요약 카드 동작을 거의 안 바꿈. 위험 최소 |

주의: 이 앱은 결과 화면의 '맞은 낱말', 요약 카드의 핵심어 세기·문장 고르기, '직접 다룬 기출 없음' 안내가 모두 **키워드 일치**에 기대고 있다. 벡터로만 올라온 문항은 맞은 낱말이 비어 있어 카드 문장 선택과 안내 기준이 어긋난다 → 벡터 결과는 '관련 기출(의미가 비슷함)'로 따로 표시하고 요약 카드 문장 생성에는 쓰지 않는 쪽이 안전하다.

## 6. 추천안과 '안 하는 게 나은 경우'

### 추천
1. **지금은 벡터를 넣지 않는다.** 1절 실패 4건 중 상당수는 값싼 방법으로 먼저 줄일 수 있다 — 일상어 사전 확장(외상값·월세·장사 접을 때·VAT…), 흔한 낱말('처리'·'신고'·'받는'·'해야')의 가중 낮추기, 어미 떼기 개선. 이 작업은 의존성이 없고 요약 카드·안내와 일관된다. (이 보고서는 그 조치를 하지 않았다; 하려면 평가셋과 분리된 질문으로 확인해야 한다.)
2. 그래도 일상어 질문이 많이 남으면, `multilingual-e5-small` ONNX + BLOB(numpy) + **'키워드가 약할 때만 보조'** 방식을 **실험 스크립트**로 먼저 만들어 동결 평가셋(30문항 이상)에서 hit@3 를 비교한다. 개선이 뚜렷하지 않으면 접는다.
3. 더 높은 품질이 필요하면 `KURE-v1` 을 시험해 보되 2.3GB 이므로 사용자가 원할 때만.

### 안 하는 게 나은 경우
- 이 앱의 주 용도가 **시험 용어로 묻는 질문**(예: '자기주식 처분손실', '수정세금계산서')이라면 현재 14/15 와 이 표본의 적중(#1·6·7·8)처럼 키워드가 충분하다. 일상어 질문이 드물면 얻는 것이 작다.
- **문제은행이 540문항**뿐이고 문항 글이 정의 설명이 아니라 객관식이라, 임베딩 유사도가 '일상어 질문 ↔ 시험 문항'을 잘 잇는지 불확실하다(문서가 짧고 표·수식이 많은 계산 문항은 특히). 의미 검색이 오히려 엉뚱한 계산 문항을 올릴 수 있다.
- 결과 화면·요약 카드·직접 기출 없음 안내가 키워드 일치에 의존하므로, 벡터를 섞으면 **설명 가능성**(왜 이 문항이 나왔는지)이 떨어진다.
- 수백 MB~2GB 모델 파일, 첫 실행 지연, 모델 없을 때의 대체 경로까지 유지해야 하는 **운영 부담**이 개인 학습 도구에는 크다.
- 대안으로 API 키가 생기면, 질문만 Claude 에 보내 '시험 용어 3~5개로 바꿔 쓰기'(질문 재작성)를 한 뒤 기존 키워드 검색에 넣는 방법이 있다. 로컬 모델이 필요 없지만 질문이 외부로 전송되고 비용이 든다. 이번엔 API 키가 필요한 검증이라 시도하지 않았다.

## 핵심 발견 요약
1. 평가셋 밖 10문항에서 적중 4·간신히 1·부분 1·실패 4 였고, 실패는 대부분 **일상어→시험 용어 간극**(외상값→대손, 장사 접을 때→폐업, 월세→주택임대소득, 월급에서 떼는 세금→원천징수)이며 'VAT'(약어)와 '처리·신고·받는' 같은 흔한 낱말의 과대 반영이 보조 원인이다.
2. 현실적인 후보는 `multilingual-e5-small`(MIT, 118M, ONNX 양자화 235MB)이고, 저장은 BLOB+numpy 가 맞다(이 Python 3.14 는 `enable_load_extension` 이 없어 `sqlite-vec` 불가, numpy·onnxruntime 은 이미 설치, 약 2일 작업). 혼합은 RRF 또는 '키워드가 약할 때만 보조'.
3. 추천은 **벡터 보류 + 사전·가중 개선 먼저**이며, 540문항·객관식 문서·키워드 일치에 기대는 카드·안내 때문에 효과가 불확실하다. 시도한다면 동결한 30문항 이상 평가셋에서 실험 스크립트로 비교하고 개선이 작으면 접는다.
